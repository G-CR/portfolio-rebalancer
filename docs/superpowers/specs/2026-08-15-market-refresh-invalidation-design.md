# 行情刷新失效策略修复设计

## 背景

`codex/usability-optimization` 与 `codex/holding-replacement` 合并后，缺失行情的自动刷新出现循环：刷新接口成功返回集合，但目标条目仍然没有有效值；mutation 随即让组合分析查询失效，持仓页在分析重新请求期间卸载缺失行情提示，重新挂载后又触发一次自动刷新。结果是失败原因与“立即重试 / 手动录入”操作无法稳定显示。

## 目标

- 刷新结果仍缺少任一必需有效值时，持仓页稳定展示供应商失败原因和恢复操作。
- 刷新结果全部具有有效值时，重新请求组合分析，使页面显示最新估值。
- 每次成功取得刷新响应后，继续更新行情缓存，并让持仓及快照查询失效。
- 不改变 HTTP 请求失败时保留缓存行情及顶栏错误提示的行为。

## 方案

在 `useRefreshMarketData` 的 `onSuccess` 中先写入最新行情缓存并递增刷新版本。随后：

1. 始终让持仓查询和快照查询失效；
2. 仅当响应中所有条目的 `effective_value` 都不为 `null` 时，让组合分析查询失效；
3. 若响应仍含缺失条目，不重新请求组合分析，让当前 `PORTFOLIO_DATA_INCOMPLETE` 状态及同一个提示组件继续存在。

该条件放在共享 mutation 层，而不是持仓页局部状态中，避免页面保存重复的服务端错误状态，也避免引入跨页面的“已自动刷新”全局标记。

## 错误处理

- HTTP 失败继续进入 mutation 的错误路径，不覆盖行情缓存。
- HTTP 成功但数据仍缺失属于可解释的业务结果，不抛异常；缺失行情提示根据响应中的 `error_summary` 展示供应商原因。
- 部分成功、部分缺失时不刷新组合分析，以免分析查询再次返回缺失错误并触发自动刷新循环。

## 测试

- 保留并使用当前已失败的 Playwright 用例，验证失败的自动刷新只发生一次，并显示“Yahoo 请求失败”“立即重试”“手动录入”。
- 增加共享行情 mutation 的单元断言：含缺失值的响应不重新请求组合分析，但仍刷新持仓和快照依赖。
- 保留成功响应测试，确认全部有效时组合分析、持仓和快照依赖都会刷新。
- 修复后运行完整前端测试、持仓 Playwright 流程，以及除已知周末邮件日期依赖外的后端完整测试。

## 验收标准

1. 缺失行情自动刷新不会循环。
2. 供应商失败原因与两个恢复操作稳定可见。
3. 有效行情刷新仍会更新依赖的分析数据。
4. 合并后的 `master` 通过上述组合验证后才推送远端。
